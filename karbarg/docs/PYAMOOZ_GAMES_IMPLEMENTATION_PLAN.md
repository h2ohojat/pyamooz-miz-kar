## ۱. نتیجهٔ نهایی که باید تحویل شود

مدیر از پنل یک فایل بازی سازگار را بارگذاری می‌کند، گزارش بررسی و پیش‌نمایش را می‌بیند، مشخصات را تکمیل و آن را منتشر می‌کند. بازی در بخش بازی‌ها و محل‌های انتخاب‌شدهٔ سایت دیده می‌شود. دانش‌آموز می‌تواند بازی را شروع کند، خارج شود، از همان نقطه ادامه دهد و نتیجه و رکورد شخصی خود را ببیند. این رفتار برای پروفایل‌های مختلف جداست.

دامنهٔ نسخهٔ اولِ کامل این برنامه:

- کتابخانهٔ بازی، جست‌وجو و فیلتر، معرفی بازی، پخش‌کننده و «بازی‌های من».
- مدیریت محتوای بازی، فایل خصوصی، نسخه‌ها، پیش‌نمایش، انتشار فوری/زمان‌بندی، توقف انتشار و بازگشت نسخه.
- ذخیره و ادامهٔ حساب و مهمان، مدیریت قطعی شبکه، جلوگیری از ثبت تکراری و تعارض دو تب.
- نتایج و رکوردهای شخصی متناسب با هر بازی؛ گزارش عملیاتی ساده برای مدیر.
- اتصال کیمیاگر اعداد و رمز استاد نقش؛ ساخت ۲۰۴۸ و سودوکو با همان قرارداد.
- راهنمای سازنده، قالب، SDK و بررسی‌کنندهٔ سازگاری؛ اثبات اضافه‌شدن بازی پنجم بدون تغییر کد اصلی سایت.
- آزمون، CI، ادغام، تحویل محلی با حفظ داده و نشست، بستهٔ انتشار و راهنمای انتشار و بازگشت.

«تکمیل بخش بازی» یعنی همهٔ این مسیرها کار کنند؛ صرف نمایش فایل داخل iframe پایان کار نیست.

## ۴. معماری اجرایی و بازاستفاده از کد موجود

```text
منبع بازی + رابط مشترک + شناسنامه
                  |
               build
                  |
         فایل HTML مستقل نسخه‌دار
                  |
      پنل: بررسی -> پیش‌نمایش -> انتشار
                  |
          Catalog و ویترین بازی‌ها
                  |
          پخش‌کنندهٔ ایزولهٔ بازی
                  |
     پل میزبان -> ذخیره / نتیجه / رکورد
                  |
          پروفایل و «بازی‌های من»
```

| نیاز | مبنای موجود | توسعهٔ موردنیاز |
| --- | --- | --- |
| ذخیرهٔ فایل و یکپارچگی | `LessonFiles` و checksum | بازاستفاده از بخش عمومی یا سرویس کوچک مشابه؛ مسیر فایل بازی جدا و خصوصی |
| بررسی HTML | `LessonInspector` و `KzMeta` | قواعد فایل مشترک؛ parser و schema مستقل بازی؛ بدون دست‌کاری رفتار درس |
| انتشار نسخه | الگوی `LessonVersion` و انتشار درس | `GameVersion` با انتشار اتمی و قواعد نسخهٔ بازی |
| اجرای امن | `LessonFileResponse` و پخش‌کنندهٔ درس | قاب و پاسخ فایل بازی با همان سطح محدودیت؛ بدون درصد/ستارهٔ مخصوص درس |
| ذخیره و تلاش | تجربهٔ `LessonAttempts` و صف مرورگر | سرویس‌های کوچک بازی با revision، idempotency و snapshot مخصوص بازی |
| هویت | `User` و `LearnerProfile` | همان احراز و پروفایل فعال؛ بدون ساخت سیستم حساب تازه |
| فهرست و جست‌وجو | `Catalog`، `Persian::normalize` و `SearchIndex` | متدهای جداگانهٔ بازی در همان Catalog؛ استفاده از نرمال‌سازی مشترک |
| خانه | `Showcase` و `HomeRow` | نوع محتوای بازی و انتخاب از پنل؛ default دادهٔ قدیمی همچنان دوره |
| ظاهر | توکن‌ها، `x-card`، `x-art`، `x-btn` و motion موجود | اجزای بازی فقط در صورت نبود جزء مناسب؛ سازگار با دو تم و کاهش حرکت |
| تنظیمات و پنل | Settings، Policy و Filament موجود | تنظیمات و مجوزهای بازی طبق همان الگو |

کلاس‌های درس به course، slide، percent و stars وابسته‌اند؛ کل آن‌ها به‌عنوان کلاس پایهٔ بازی استفاده نشوند. ابتدا بخش واقعاً مشترک شناسایی شود؛ استخراج بزرگ چارچوب عمومی شرط شروع این کار نیست. نصب بسته یا زیرساخت جدید نیاز پیش‌فرض ندارد.

## ۵. مدل دادهٔ هدف و قواعد آن

نام‌های زیر پیشنهاد اجرایی‌اند؛ در G03 با الگوی دقیق مدل‌ها و migrationهای همان نسخهٔ میزبان نهایی می‌شوند.

| موجودیت | داده‌های اصلی | قاعدهٔ حیاتی |
| --- | --- | --- |
| `games` | شناسهٔ ثابت محتوا، slug، عنوان/شرح/راهنما، تصویر، وضعیت، ترتیب، نسخهٔ فعال، متن جست‌وجو | شناسه یکتا؛ عنوان و اطلاعات ویترین قابل مدیریت؛ بدون الزام course |

| رابطه‌های محتوا | دسته‌ها/مفهوم‌ها/پایه‌ها در صورت نیاز | از taxonomy موجود استفاده شود؛ category دوره بدون بررسی رفتار مشترک تغییر نکند |

قواعد تکمیلی:

1. بانک فقط دادهٔ حساب معتبر را نگه دارد؛ مهمان برای ذخیرهٔ شخصی از فضای میزبان در همان مرورگر استفاده می‌کند. شناسهٔ نوبت مهمان توسط میزبان ایجاد می‌شود، نه بر مبنای نام دانش‌آموز.
2. پیشنهاد نسخهٔ اول: برای هر پروفایل/بازی/ترکیب تنظیمات یک دور قابل ادامه وجود داشته باشد. رقابت دو درخواست شروع با تراکنش/قید مناسب کنترل شود؛ شروع دوباره، نوبت تازه است و دور قبلی پس از انتخاب روشن کاربر رهاشده می‌شود.
3. ایندکس و قید یکتایی برای شناسهٔ بازی، نسخهٔ بازی، receipt ذخیره، نتیجهٔ نوبت و رکورد هر گروه لازم است. تعداد جدول‌ها بهانه‌ای برای ایجاد سیستم event-sourcing یا ثبت تک‌تک حرکت‌ها نیست.
4. گروه مقایسهٔ رکورد از قواعد معتبر نسخه و تنظیمات می‌آید؛ امتیاز نسخه‌های دارای قانون متفاوت، حالت راهنما و سختی متفاوت مخلوط نشود. تعریف اجرایی این گروه در G01 نهایی می‌شود.
5. حذف/غیرفعال‌سازی پروفایل و حساب باید داده و دسترسی بازی را نیز طبق سیاست فعلی سایت پوشش دهد؛ snapshot و شناسهٔ شخصی در log عمومی ثبت نشود.
6. حذف نسخه‌ای که run فعال به آن متصل است مجاز نباشد. توقف امنیتی نسخه از نگه‌داری آن برای ادامه مقدم است؛ پیام مناسب و سیاست حفظ داده لازم است.
7. جدول‌های جدید با migration افزایشی اضافه شوند. rollback عادی برنامه نباید به حذف جدول‌ها و ازبین‌رفتن بازی‌های ذخیره‌شده متکی باشد.

## ۶. مسیرهای کاربران و پنل

### دانش‌آموز و مهمان

| مقصد پیشنهادی | تجربهٔ لازم |
| --- | --- |
| `/games` | کارت‌های واقعی، جست‌وجو، فیلتر، پاک‌کردن، تعداد نتیجه، صفحه‌بندی و حالت خالی |
| `/games/{slug}` | معرفی کوتاه، مهارت/سختی، روش بازی، شروع یا ادامه و محدودیت ذخیرهٔ مهمان |
| `/games/{slug}/play` | قاب متمرکز، راهنما، توقف، صدا، خروج/تمام‌صفحه و وضعیت ذخیره |
| `/dashboard/games` | ادامهٔ بازی‌ها، نتیجه‌های اخیر و رکوردهای همان پروفایل |
| نتیجهٔ نوبت | برد/باخت/اتمام، معیارهای مناسب، دور تازه و بازگشت به بازی‌های من |

URLها نام‌های پیشنهادی این برنامه‌اند؛ پیش از پیاده‌سازی با routeهای موجود تطبیق داده و از named route استفاده شوند. شروع نوبتِ ماندگار و عملیات تغییر داده با POST دارای CSRF انجام شود؛ refresh صفحه یا GET معرفی بازی نوبت اضافه نسازد.

جریان مهمان: دیدن بازی -> شروع -> ذخیره در همین مرورگر -> پیشنهاد کم‌مزاحمت ورود برای ادامه روی دستگاه دیگر. پس از ورود، انتقال بازی مهمان تنها به پروفایل فعال و با انتخاب روشن انجام شود؛ وجود ذخیرهٔ حساب تعارض است و بی‌صدا بازنویسی نمی‌شود.

جریان حساب: انتخاب پروفایل -> شروع/ادامه -> ذخیرهٔ تأییدشده -> خروج -> ادامه روی همان یا دستگاه دیگر. تغییر پروفایل و logout اجرای قبلی را متوقف و مجوز پیام‌های معوق را دوباره بررسی کند. ماندگاری ورود ۹۰روزهٔ موجود حفظ شود.

### مدیر و سازنده

پنل: بارگذاری فایل -> بررسی ایستا -> پیش‌نمایش ایزوله و گزارش اتصال -> تکمیل مشخصات -> انتخاب انتشار -> مشاهدهٔ وضعیت. بررسی ایستا، پیش‌نمایش runtime و انتشار سه وضعیت جدا هستند؛ تأیید یک شناسنامه معادل بازی سالم نیست.

ویرایش عنوان، تصویر، ترتیب و دسته از پنل انجام می‌شود؛ تغییر قواعد بازی یا فایل نیازمند نسخهٔ تازه است. سابقهٔ نسخه‌ها، مقایسهٔ قرارداد/ذخیره، بازگشت، توقف انتشار و هشدار ناسازگاری در دسترس مدیر باشند. خطای شبکهٔ پنل و بارگذاری تکراری نباید نسخه یا انتشار تکراری بسازد.

- آخرین وضعیت تست‌های پروژه ثبت و مشکل‌های قبلی از تغییر تازه تفکیک شوند. دادهٔ واقعی مالک برای آزمون تخریبی استفاده نشود.
- تصمیم‌های پایهٔ بخش ۲ و مرز انتشار ثبت شوند؛ هیچ ویژگی جانبی به‌طور ضمنی وارد دامنه نشود.

**پذیرش:** هر کار اجرایی صاحب، محدوده، وابستگی و معیار تحویل دارد؛ نقطهٔ شروع و تغییرات موجود معلوم‌اند. خروجی این مرحله توسعهٔ بازی نیست.

### G01 — بستن جزئیات قرارداد و داده‌های آزمون مشترک

- از قرارداد موجود، schema و fixture معتبر/نامعتبر برای manifest، hello/init، state، ack، نتیجه و خطا استخراج شود. PHP و JavaScript باید نمونه‌های یکسان را یکسان قبول یا رد کنند.
- ابهام‌های اجرایی پیش از ساخت دو سوی پل حل و در همان قرارداد ثبت شوند: timeout و hello تکراری؛ نگه‌داری snapshot نهایی هنگام نتیجه؛ receipt تکراری پس از reconnect؛ تنظیمات و گروه رکورد؛ پایان‌دادن آگاهانه به run و تخصیص دور جدید.
- تنظیمات معتبر مشترک مانند زبان، تم، کاهش حرکت و صدا، و تنظیمات هر بازی مثل سختی باید schema، مقدار پیش‌فرض و محدودهٔ مجاز داشته باشند. عوض‌شدن تنظیم مؤثر بر قواعد در میانهٔ دور، به‌جای تغییر خاموش گروه رکورد، دور تازه یا سیاست صریح می‌خواهد.
- اصل نتیجهٔ نهایی: میزبان فقط پس از ثبت قطعی آخرین وضعیت موردنیاز و نتیجه، موفقیت اعلام کند؛ روش انتقال/هماهنگی در قرارداد نهایی مشخص شود، نه اینکه هر بازی روش خودش را بسازد.
- روش compare-and-swap برای revision و پاسخ تعارض مستند شود. هویت، پروفایل و نسخه از زمینهٔ سرور تعیین می‌شوند؛ ادعای client کافی نیست.
- نسخهٔ قرارداد پشتیبانی‌شده در میزبان و SDK قابل خواندن باشد؛ پیام یا schema ناشناخته با خطای روشن رد شود.

**پذیرش:** مجموعهٔ نمونهٔ مشترک و قرارداد بدون ابهام برای پیاده‌سازی آماده است؛ هیچ API خیالی به محتوای تولیدی اضافه نشده است.

### G02 — SDK سبک و میزبان آزمایشی

- در مخزن محتوا، رابط مشترک کوچک برای handshake، snapshot، restore، pause، result و مدیریت خطا ساخته شود. قواعد بازی وارد SDK نشوند.
- حالت مستقل از حالت embedded جدا باشد؛ قطع دسترسی localStorage یا نبود میزبان بازی را خراب نکند. در embedded پیش از init معتبر، ذخیرهٔ حساب و ادامهٔ قبلی حدس زده نشود.
- میزبان آزمایشی با همان sandbox/CSP، امکان نمایش پیام‌ها و تزریق خطای ذخیره، ack دیرهنگام، تعارض و نسخهٔ ناسازگار داشته باشد؛ ابزار آزمون وارد محصول دانش‌آموز نشود.
- build بازی‌ها فقط بستهٔ منتخب را بتواند بسازد و شناسنامه/SDK واقعی را جاسازی کند؛ خروجی‌های دیگر بی‌دلیل بازنویسی نشوند.
- یک بازی کوچک آزمایشی و بخش محدود از کیمیاگر، ذخیرهٔ منطقی و بازیابی را ثابت کنند. انتقال کامل محتوای کیمیاگر در G10 است.

**پذیرش:** وسط یک دور، snapshot گرفته و پس از بارگذاری مجدد همان وضعیت برگردد؛ پیام تکراری یا init دوباره بازی را reset نکند. این هنوز جای آزمون میزبان واقعی را نمی‌گیرد.

### G03 — مدل داده، مجوزها و فایل خصوصی

- مدل‌ها، migrationها، factoryها و قیدهای بخش ۵ ساخته شوند؛ با SQLite آزمون و MySQL مقصد سازگار باشند.
- Policyهای دیدن، اجرا، پیش‌نمایش، مدیریت و دریافت فایل روشن باشند. شاخهٔ کارکنان با دادهٔ پیش‌نمایش از آمار دانش‌آموز جداست.
- فایل بازی خارج public با نام/مسیر امن، checksum، بررسی اندازه و مالکیت نسخه نگه‌داری شود. path ورودی کاربر مستقیماً مسیر دیسک نشود.
- الگوی دسته، مفهوم، تصویر و PublishStatus موجود به‌کار رود. برای بازی جدول کاربر یا پروفایل تازه ساخته نشود.

**پذیرش:** کاربر غیرمجاز فایل خصوصی/نسخهٔ پیش‌نویس را نمی‌گیرد؛ migration روی دادهٔ قبلی درس اثر ناخواسته ندارد؛ قید یکتایی جلوی ساخت نسخه و نتیجهٔ تکراری را می‌گیرد.

### G04 — بررسی و ورود نسخهٔ بازی

- inspector بدون اجرای کد، UTF-8، HTML کامل، اندازه، منابع داخلی، JSON، شناسه‌ها، نسخه‌ها، قابلیت‌ها، levels و metrics را بررسی کند.
- بلوک تکراری شناسنامه، نوع نادرست، مقدار غیرمتناهی/بسیار بزرگ، دادهٔ نامعتبر و نسخهٔ پشتیبانی‌نشده رد شوند. حد اندازه و عمق داده در اعتبارسنجی مشخص شود.
- نام/نسخه/بازیِ فایل با مقصد پنل تطبیق یابد. فایل یکسان ورود تکراری نسازد؛ یک شناسه و نسخه با checksum متفاوت تعارض است، نه جایگزینی خاموش.
- تفاوت schema ذخیره و قرارداد نسخهٔ قبلی گزارش شود. واردکردن فایل فقط draft ایجاد کند؛ تنظیمات دستی ویترین هنگام آپلود نسخهٔ جدید بی‌صدا حذف نشوند.
- خطای نیمه‌کارهٔ DB یا دیسک بازیابی شود؛ پاک‌سازی فایل orphan فقط پس از بررسی ارجاع و با حفظ فایل نسخه‌های فعال باشد.

**پذیرش:** فایل سالم draft قابل پیش‌نمایش می‌شود؛ فایل ناسازگار دلیل فارسی قابل اقدام دارد؛ دوباره‌فرستادن فرم نسخهٔ اضافه نمی‌سازد.

### G05 — پخش‌کننده و چرخهٔ نوبت

- صفحهٔ بازی از اجزای موجود و iframe محدود ساخته شود؛ فایل از مسیر محافظت‌شده و با کنترل مجوز هر درخواست تحویل داده شود.
- شروع و ادامهٔ نوبت با request id، زمینهٔ حساب/پروفایل معتبر و نسخهٔ ثابت انجام شود. GET یا refresh، run جدید نسازد.
- timeout بارگذاری، خطای اتصال پل، فایل خراب/حذف‌شده، لغو انتشار و نسخهٔ ممنوع، حالت‌های فارسی با اقدام مناسب داشته باشند.
- پل source/session/run/نسخه و payload را کنترل کند؛ انتقال پیام از iframe دیگر یا namespace درس پذیرفته نشود.
- کنترل‌های توقف، راهنما، صدا، خروج و تمام‌صفحه روشن باشند. اگر Fullscreen API در مرورگر قابل استفاده نبود، حالت متمرکز عادی کار کند.

**پذیرش:** بازی آزمایشی از مسیر واقعی سایت و پیش‌نمایش مدیر اجرا شود، handshake درست باشد و هیچ دادهٔ پیش‌نمایش وارد نتایج واقعی نشود.

### G06 — ذخیره، ادامه، نتیجه و رکورد

- endpointهای ذخیره و نتیجه با Form Request، CSRF، Policy، محدودیت نرخ و تراکنش ساخته شوند؛ payload حداکثر قرارداد کنترل شود.
- ack فقط پس از ثبت داده صادر شود؛ پاسخ گم‌شده با ارسال مجدد همان receipt نتیجهٔ تکراری نسازد. صف مرورگر snapshot جدید را با ack قدیمی پاک نکند.
- نسخهٔ فعال نوبت ثابت بماند؛ compare-and-swap تعارض دو تب/دستگاه را تشخیص دهد و کاربر انتخاب روشن برای ادامهٔ آخرین وضعیت یا شروع دور جدا داشته باشد.
- کش حساب، مهمان و پروفایل‌ها جدا باشد. قطع شبکه، refresh، bfcache، logout و تغییر پروفایل آزمایش شوند. انتخاب بازکردن دادهٔ سرور یا pending محلی بر پایهٔ revision/مالک باشد، نه فقط ساعت دستگاه.
- مهاجرت اختیاری ذخیرهٔ مهمان به پروفایل انتخاب‌شده idempotent باشد؛ هرگز دادهٔ حساب دیگر منبع انتقال نشود.
- نتیجهٔ نهایی، state نهایی لازم و رکورد با ترتیب/تراکنش تعریف‌شده ثبت شوند. رهاکردن، باخت، برد و خروج موقت فرق دارند؛ نتیجهٔ قدیمی run تازه را تغییر ندهد.
- رکورد برای metric و گروه معتبر از نتیجه ساخته شود؛ عدد منفی یا نام معیار ناشناخته پذیرفته نشود. سیستم ادعای ضدتقلب کامل نکند.

**پذیرش:** سناریوی واقعی «بازی کن، شبکه را قطع کن، تغییر بده، برگرد، ادامه بده» داده را حفظ کند؛ نتیجهٔ تکراری رکورد/شمارش را زیاد نکند؛ دو پروفایل هیچ اختلاطی نداشته باشند.

### G07 — پنل کامل مدیریت و انتشار

- Resource بازی و مدیریت نسخه‌ها، بارگذاری مرحله‌ای، گزارش بررسی، پیش‌نمایش و تنظیم مشخصات ساخته شوند.
- مدیر بتواند تصویر، توضیح، راهنما، دسته، پایه/مفهوم، ترتیب، برچسب و تنظیمات داده‌ای مجاز بازی را ویرایش کند.
- پیش‌نمایش سلامت پل را گزارش کند؛ عبور دستی از خطای بحرانی شناسنامه/فایل مجاز نباشد. تست اتصال خودکار جای بازبینی محتوای آموزشی را نگیرد.
- draft، coming-soon، published و hidden رفتار روشن داشته باشند؛ نمایش «به‌زودی» به‌معنی مجوز اجرا نیست. توقف امنیتی نسخه با hidden شدن ویترین فرق دارد.
- سیاست پایه: hidden بازی را از ویترین و شروع عمومی تازه خارج می‌کند؛ ادامهٔ run قبلی فقط با نسخه و مجوز هنوز معتبر ممکن است. نسخهٔ متوقف‌شده به دلیل امنیت برای هیچ run تحویل داده نمی‌شود. تصمیم متفاوت باید در Policy و قرارداد تحویل ثبت شود.
- انتشار فوری، زمان‌بندی با تقویم شمسی/UTC موجود، rollback نسخه و نمایش اثر بر ذخیره‌های قبلی فراهم شود. cron فعلی برای انتشار زمان‌بندی‌شده گسترش یابد؛ سرویس جدا لازم نیست.
- اجازهٔ حذف، فایل‌های ارجاع‌شده، history نسخه و idempotency انتشار کنترل شوند. بازگرداندن نسخه نباید فایل جدید را روی فایل قدیمی بنویسد.

**پذیرش:** مدیر یک بازی را از پنل تا اجرای واقعی منتشر، پنهان، زمان‌بندی و به نسخهٔ قبلی برگرداند؛ هم‌زمان runهای مجاز قبلی سیاست ادامهٔ مشخص داشته باشند.

### G08 — کتابخانه و جست‌وجوی بازی

- فهرست، کارت و صفحهٔ معرفی با دادهٔ واقعی Catalog ساخته شوند؛ تصویر و حالت خالی مطابق اجزای سایت باشند.
- متن جست‌وجو با نرمال‌سازی فارسی از مشخصات منتشرشده ساخته و هنگام تغییر پنل تازه شود. عنوان، خلاصه، دسته و مهارت‌های مجاز قابل جست‌وجو باشند.
- فیلترهای قابل فهم مانند دسته، نوع و سطح از دادهٔ واقعی بیایند؛ فیلتر بی‌داده نمایش داده نشود. query در URL و عقب/جلو مرورگر حفظ شود.
- رفتار جست‌وجوی موجود بازاستفاده شود: تایپ با مکث، Enter فوری، کنترل ورودی ترکیبی، پاسخ کهنه، پاک‌کردن و retry؛ فوکوس کاربر نپرد.
- بدون JavaScript فهرست/معرفی و جست‌وجوی GET قابل استفاده باشد؛ اجرای بازی نیاز به JavaScript را روشن بگوید. عنوان و توضیح صفحهٔ منتشرشده برای اشتراک‌گذاری درست باشند؛ صفحات خصوصی/بازی نیمه‌تمام index نشوند.

**پذیرش:** بازی تازهٔ منتشرشده از پنل بدون تغییر کد در جست‌وجو پیدا شود؛ پنهان/پیش‌نویس در نتیجهٔ عمومی نشت نکند؛ شمار بازی با شمار دوره مخلوط نشود.

### G09 — بازی‌های من، ناوبری و ویترین خانه

- داشبورد اصلی یک ورودی/بخش بازیِ متمایز داشته باشد؛ ستاره‌ها، هدف هفتگی و پیشنهاد درس موجود تغییر معنا ندهند.

**پذیرش:** بازی از خانه/ناوبری قابل کشف و از داشبورد قابل ادامه است؛ خانه و جست‌وجوی دوره‌های قبلی بدون رگرسیون کار می‌کنند.

## ۹. قواعد اجرای Issue، آزمون و ادغام

1. یک Issue، یک صاحب و یک PR در هر مخزن؛ شاخه از آخرین main طبق `codex/P1-<شماره>-games-<شرح>` یا قرارداد جاری عامل مربوط ساخته شود. PR باز عامل دیگر ابتدا تعیین تکلیف شود.
2. هر مرحلهٔ بزرگ به Issue کوچک‌تر شکسته شود، اما معیار اصلی مرحله حذف نشود. تغییر هم‌زمان فایل مشترک بزرگ مانند Catalog، Showcase و tokens بدون هماهنگی انجام نشود.
3. قبل از کدنویسی `.ai/rules` و قواعد مسیر، اگر موجودند، خوانده شوند. schema و تست نمونه قبل از اتصال پراکندهٔ چند بازی آماده باشند.
4. تغییرات میزبان: آزمون مرتبط، سپس `php artisan test`، `vendor/bin/pint --dirty`، `npm run build` و آزمون‌های Node موجود/تازه اجرا شوند. از نام واقعی دستورها در نسخهٔ جاری استفاده شود؛ `npm test` در package فعلی تعریف نشده است.
5. دو job فعلی CI میزبان، `Tests, Pint, build` و `Deploy package (no .env, no caches)` روی همان head تحویلی موفق باشند. آزمون‌های تازهٔ پل بازی به job موجود افزوده شوند.
6. مخزن محتوا نیز آزمون منطق بازی، bridge و build محدودِ فایل‌های تغییرکرده را داشته باشد؛ اگر CI آن این موارد را ندارد، در همان محدوده تکمیل شود. سبز بودن CI سایت جای آزمون منبع بازی را نمی‌گیرد.
7. PR رابط شامل تصاویر واقعی گوشی، تبلت و دسکتاپ و نتیجهٔ بررسی دو تم/کاهش حرکت است. PR داده/عملیات شامل migration و الزامات انتشار است.
8. پس از بازبینی و موفقیت CI، ادغام مطابق اختیار و روند ثبت‌شدهٔ پروژه انجام شود. merge یک مرحله به‌معنی انتشار عمومی یا اتمام کل بازی‌ها نیست.
9. تحویل هر مرحله شامل: چه چیزی عوض شد، چرا، کدام آزمون روی کدام commit، لینک PR/Issue، موارد باز و مرحلهٔ بعد است.

```text
وضعیت: برنامه‌ریزی‌شده | در حال انجام | در بازبینی | ادغام‌شده | تحویل‌شده | وابستگی باز
صاحب:
مخزن / Issue / شاخه / PR:
commit آزموده‌شده:
معیارهای پذیرش انجام‌شده:
آزمون‌ها و شواهد:
محدودیت یا وابستگی باز:
کار بعدی:
```
